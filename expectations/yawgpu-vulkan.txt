# F-085: sample_mask fragment builtin under Vulkan per-sample dispatch (@interpolate(...,sample)
# at sampleCount=4) — the sample_mask input is the current sample's single bit (Vulkan
# semantics) where the current CTS oracle expects the full coverage mask. NOT an implementation
# defect: yawgpu, wgpu-native and Dawn all behave this way on Vulkan (Dawn suppresses these
# cases, crbug.com/407144390); the WGSL WG resolved to respecify sample_mask to the Vulkan
# single-bit semantics (gpuweb/gpuweb#5457; CTS change gpuweb/cts#4510 pending). Drop these
# entries when cts#4510 merges and the port's oracle is updated.
#
# The sibling inputs,position cases were formerly xfail'd here too (position was thought to be
# equally spec-in-flux, gpuweb#4777), but the Dawn oracle now PASSES them by reconstructing the
# pixel center for @builtin(position) under sample-rate shading. yawgpu implements the same
# polyfill (see FINDINGS.md F-085), so position is a real pass and is no longer xfail'd here.
webgpu:shader,execution,shader_io,fragment_builtins:inputs,sample_mask:nearFar="[0,1]";sampleCount=4;interpolation="linear,sample"
webgpu:shader,execution,shader_io,fragment_builtins:inputs,sample_mask:nearFar="[0,1]";sampleCount=4;interpolation="perspective,sample"
webgpu:shader,execution,shader_io,fragment_builtins:inputs,sample_mask:nearFar="[0.25,0.75]";sampleCount=4;interpolation="linear,sample"
webgpu:shader,execution,shader_io,fragment_builtins:inputs,sample_mask:nearFar="[0.25,0.75]";sampleCount=4;interpolation="perspective,sample"

# F-129 (CLOSED): denormal fwidth value mismatch on native Vulkan — NOT a yawgpu defect.
# fwidth/fwidthFine/fwidthCoarse f32 fail near the denormal boundary, e.g.
# inputs=(-10, -FLT_MIN, …) → expected[3]=[3.52648e-38, 4.70198e-38]; got 4.70198e-38 (the got value is
# the acceptance interval's own upper endpoint — the CTS-computed interval is marginally too tight for the
# NVIDIA Vulkan denormal result). The Dawn-Vulkan oracle (same GPU + API, built this host) fails all 8
# f32 cases with the byte-identical value, so this is a CTS acceptance-interval / NVIDIA-denormal artifact
# (F-104/F-090-class), not a yawgpu/naga defect. The separate `discard`+derivative SPIR-V gap (sub-cause 1)
# was a real defect and is FIXED in yawgpu's naga fork (demote-to-helper), so it is not listed here.
# Drop these if the upstream gpuweb/cts fwidth acceptance interval is widened for denormals.
# NVIDIA-host-specific: these PASS on Intel/ANV (xpass confirmed 2026-07-04).
webgpu:shader,execution,expression,call,builtin,fwidth:f32:*
webgpu:shader,execution,expression,call,builtin,fwidthFine:f32:*
webgpu:shader,execution,expression,call,builtin,fwidthCoarse:f32:*

# F-141: memory_model,coherence:corr (atomic_storage, intra_workgroup) -- NOT a yawgpu defect.
# This NVIDIA RTX 5060 Ti reliably (4/4) exhibits a storage-atomic intra-workgroup memory-ordering
# relaxation that WebGPU's memory model disallows ("disallowed weak behavior observed",
# testResults[3] != 0). Dawn -- the reference impl -- fails the SAME case identically on the SAME GPU
# (statistical test, so counts differ, but both reliably observe it), so this is a hardware/driver
# memory-model property, not yawgpu and not a CTS-port oracle bug. Distinct from F-112 (atomic_workgroup
# corr, a real yawgpu defect, RESOLVED). Unchanged by yawgpu bd21cfb's VK_KHR_vulkan_memory_model.
# Drop if the NVIDIA driver or the upstream CTS corr tuning changes (would xpass). See docs/FINDINGS.md F-141.
# NVIDIA-host-specific: passes on Intel/ANV (xpass confirmed 2026-07-04).
webgpu:shader,execution,memory_model,coherence:corr:memType="atomic_storage";testType="intra_workgroup"
# F-152: the same corr test on the WORKGROUP memType -- NOT a yawgpu defect. On the Linux /
# NVIDIA RTX 5060 Ti host (driver 595.91) this variant reliably observes the disallowed weak
# behavior (5/5) while atomic_storage passes -- the mirror image of the Windows host. Dawn built
# against the same GPU and driver fails and passes the two variants identically, so it is a
# hardware/driver memory-model property, not yawgpu and not a regression of F-112. Which of the
# two variants fires is host-dependent, so both are listed and the one that does not fire xpasses
# benignly. See docs/FINDINGS.md F-152.
webgpu:shader,execution,memory_model,coherence:corr:memType="atomic_workgroup";testType="intra_workgroup"
