# fix-parsequery-colon-in-quoted-value — parseQuery must not split on `:` inside the params blob

> Bug fix. `parseQuery` over-splits case queries whose param values contain `:` (e.g.
> `offsetVariant="0:0"`), so `--run-case` rejects them as "invalid query" — which breaks **all of
> `--isolate`** (serial and the H3 `--workers` pool) for those cases. Pre-existing defect, surfaced by
> the first full-suite isolated run. Implementation by the coding agent. See
> [`reference/workflow.md`](reference/workflow.md).

## Background / evidence

A full-suite `--isolate --workers 8` run on yawgpu/Vulkan (2026-06-15, 234 queries) reported
`fail=616`, of which **612 were `invalid query: …`**, not real test failures. Reproduced minimally:

```
cts 'webgpu:api,validation,render_pipeline,vertex_state:vertex_attribute_offset_alignment:*'                    -> pass=10584 fail=0   (in-process: clean)
cts --isolate            'webgpu:…:vertex_attribute_offset_alignment:*'                                          -> fail=588 (all "invalid query")
cts --isolate --workers 4 'webgpu:…:vertex_attribute_offset_alignment:*'                                         -> fail=588 (identical to serial)
```

Serial `--isolate` and the H3 pool fail **identically** — so the H3 pool is correct; the defect is in
the shared `--run-case` path, specifically `parseQuery`.

**Root cause** (`src/common/query.cpp:36-47`): `parseQuery` does `split(text, ':')` and rejects when
`parts.size() > 4`. A case query is `webgpu:<file>:<test>:<params>`, and the `<params>` blob can
legitimately contain `:` inside a quoted string value. Example failing query (generated by
`caseQuery`/`stringifyParams` and fed back via `--run-case`):

```
webgpu:api,validation,render_pipeline,vertex_state:vertex_attribute_offset_alignment:format="uint8";arrayStrideVariant_mult=0;arrayStrideVariant_add=256;offsetVariant="0:0"
```

splits into **5** parts (the `:` inside `"0:0"` adds one) → `parts.size() == 5 > 4` → thrown as
"invalid query". In-process runs never hit this because they match via `queryMatchesCase`
(`query.params == stringifyParams(params)`), never re-parsing the stringified blob.

## Fix

`parseQuery` must split into **at most 4 segments**: `suite`, `file`, `test`, and `params` =
**everything after the 3rd `:`** (kept verbatim, may contain `:`). The `<file>` segment
(`api,validation,…`) and `<test>` name never contain `:`, so splitting on the first three colons is
correct and unambiguous.

Concretely, replace the unbounded `split(text, ':')` + size check with a bounded split (3 colons →
4 fields, the last field is the remainder). Suggested shape (keep the existing validation intent):

- Find the 1st, 2nd, 3rd `:`. Require at least 2 colons (suite:file:test) and `suite == "webgpu"`.
- `suite`/`file`/`test` = the first three fields; `params` = substring after the 3rd colon, or `"*"`
  when there is no 4th segment (i.e. only `webgpu:file:test`).
- Preserve current behavior for the 3-segment form (`webgpu:file:test` → `params = "*"`), the
  trailing `:*` form (`…:test:*` → `params = "*"`), and the empty-params form
  (`…:test:` → `params` empty → treated as `*` downstream, unchanged).
- Keep throwing `std::runtime_error("invalid query: " + text)` for genuinely malformed input
  (< 3 segments, or `suite != "webgpu"`).

Do **not** change `stringifyParams`/`stringifyValue`/`caseQuery` (the producer side is correct — the
round-trip is what must be restored), and do not change `queryMatchesCase`. Only `:` over-splitting is
the bug; commas/semicolons live entirely inside the params blob and are compared as one string, so
they need no special handling once params is captured whole.

## Scope

**In:** `parseQuery` in `src/common/query.cpp` + a `cts_unittests` round-trip test.

**Out:** the stringify/producer side, the isolation/pool code (it is correct), expectations, docs,
specs. No git.
